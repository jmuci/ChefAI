| 004 | [Data Layer Composition](../adrs/adr-004-data-layer.md) | Nov 2025 | Repositories over Room DAOs; the outbox is each row's `syncState`, not a table. Sync lives in `SyncOrchestrator`, not repositories (amended). |
| 005 | [Feature-Based Packages](../adrs/adr-0005-feature-based-package-structure.md) | Nov 2025 | Feature packages over layer packages. Start in feature, move to core/ when shared. |
| 006 | [Sync Protocol](../adrs/adr-006-sync-protocol.md) | Mar 2026 | Push before pull, aggregate-level recipes, last-writer-wins on `updatedAt`. WorkManager triggers: login, foreground, 5s mutation debounce, pull-to-refresh, daily periodic on a charger. Supersedes ADR-003. |
| 007 | [Anonymous-First Accounts](../adrs/adr-007-anonymous-first.md) | Feb 2026 | Recipes exist before accounts do. Login/registration re-parents local data to the new user UUID locally (`AccountUpgradeUseCase`); no upgrade endpoint. |
| 008 | [Data Across Sessions](../adrs/adr-008-data-handling-across-sessions.md) | Mar 2026 | Logout keeps local data. A *different* user logging in from an anonymous session keeps the anonymous work, drops everything the previous account left (recipes + images, plans, saved plans, bookmarks, cook events, pull cursor), and upgrades the rest; otherwise Room and `recipe_images/` are cleared. |
| 009 | [Navigation-Scoped ViewModel for Wizards](../adrs/adr-009-navigation-scoped-viewmodel-for-wizards.md) | Mar 2026 | Multi-screen wizard flows use a nested NavGraph-scoped ViewModel; state lives exactly as long as the flow. |
| 010 | [Client-Side Recipe URL Scraping](../adrs/adr-010-client-side-recipe-scraping.md) | Aug 2026 | Paste-a-URL import scrapes JSON-LD/microdata on-device via a new pure-Kotlin `:recipe-scraper` module; no backend endpoint, no per-site scrapers, unauthenticated `@ScraperHttpClient` prevents auth-token leakage to third-party hosts. Decision 5 (Aug 2026) adds a rendered-DOM fallback — an off-screen `WebView`, then a visible one — for the minority of sites that refuse HTTP clients outright. Decision 6 (Aug 2026) caches the imported hero image on-device via the same fetch-then-WebView ladder, since the same CDNs that block the HTML fetch block their own images too; the cached path is device-local only, not synced (see ADR-011). Decision 7 (Aug 2026, #179) hardens the SSRF guard to resolve DNS and check actual `InetAddress`es (closing a DNS-rebinding gap and covering IPv6) and re-validates every redirect hop instead of trusting the original URL. |
| 011 | [Cross-Device Recipe Images](../adrs/adr-011-cross-device-recipe-images.md) | Aug 2026 | Image bytes never ride the JSON sync payload. Scraped images are re-derived per device by a charging + unmetered backfill worker; (Decision 1 — user-authored-only uploads — superseded by ADR-012.) A blank `imageUrl` means "user's own image, cannot be re-derived". Blob state lives in `recipe_image_state`, never on `recipes`, so the full-row upsert on the pull path can't wipe it. |
| 012 | [Recipe Image Upload (Stage 2)](../adrs/adr-012-recipe-image-upload.md) | Aug 2026 | Supersedes ADR-011 Decision 1: **every** recipe image is stored server-side, scraped as well as user-taken, and served to anyone who may see the recipe (`PRIVATE` still 404s for non-owners). A server-owned `imageBlobId` content hash rides `SyncRecipeDto` while the bytes never do; the backfill worker gains a preferred tier fetching it over an authenticated GET, so Coil never talks to our backend and no JWT can reach a third-party CDN. Upload is a post-sync sweep gated on `syncState = 'SYNCED'`, unmetered but not charging-only. Publicly serving scraped images is an accepted compliance posture, revisited at ~50 users ([#144](https://github.com/jmuci/ChefAI/issues/144)) and reversible by two server config flags. |
| 013 | [Measurement Unit Conversion](../adrs/adr-013-measurement-unit-conversion.md) | Aug 2026 | A profile setting (`As written` / `Metric` / `Imperial`) re-expresses ingredient amounts **at display time only** — `recipe_ingredients` is never written, so "As written" always restores the original exactly. Dimensional conversion (volume→volume, mass→mass) is the floor; a curated ~40-staple density table in `core/domain/units/IngredientDensity` is the only thing that crosses cups↔grams, marked `≈`, and suppressed for `chopped`/`shredded`/`grated`… names. Counting units (`clove`, `can`, `pinch`, the scraper's `"unit"`) never convert — `UnitNormalizer` models the convertible set and returns `null` for everything else. Cup = US customary 236.59 ml, a stated assumption. Preference is device-local DataStore (`chefai_user_prefs`), not synced, defaulting to `AS_WRITTEN` so no existing library changes on update. |
| 014 | [Households](../adrs/adr-014-households.md) | Sep 2026 | Sharing a meal plan/grocery list with a household is a **scope layer**, not an ownership migration — `recipes.creator_id` is untouched, and only a nullable `meal_plans.householdId` plus a new gap clause in the backend's recipe sync widen visibility. Household membership folds into `UserSession.Authenticated` (`household: AuthenticatedHousehold?`) rather than a parallel state; household CRUD (create/invite/accept/leave) is plain REST, not the sync protocol, and its local cache tables are wholesale-replaced on refresh, never pushed. `shopping_list_checks` becomes a `SyncableCrossRef` (composite-keyed, like `BookmarkedRecipeEntity`) with an explicit `checked` column (Room v8→v9), synced with last-writer-wins; the list shows who checked an item. Existing rows backfill `SYNCED`, not `PENDING` — a pre-existing tick is a historical fact, not a new edit to push. |
| 015 | [The Meal Plans Week View](../adrs/adr-015-meal-plans-week-view.md) | Sep 2026 | **Date-first**: seven dated rows that every live plan is projected onto. Day 0 is `MealPlan.startDate` (DB v13; `createdAt` fallback). Overlapping plans all show, tagged by plan. Header is Week \| Plans (the Just me/Family toggle is gone). "+ Add meal" opens the wizard seeded with the picked recipe and date. Decisions 2, 3 and 5 are superseded by amendments — read the ADR's "Current state" box. |
| 016 | [Recipe Language](../adrs/adr-016-recipe-language.md) | Oct 2026 | Recipes store an ISO 639-1 code (`recipes.language`, nullable, raw `String` in the domain so a full-row write never erases an unknown code). `:recipe-scraper` detects it by weighing the highest-priority markup signal (`inLanguage` → `<html lang>` → `og:locale` → content-language meta → HTTP header) against stop-word scoring over six language profiles — text wins a disagreement but only at `LOW` confidence. Ingredient lines are re-parsed with the detected language: Spanish unit words are a union with English (never collide), only connector words (`de`, `"2 a 3"`, bare `c`) are gated, so a wrong guess costs little. The editor asks only when unsure (dialog on open and again on Save; confirming from Save continues the save); a device-local **fallback language** setting pre-ticks the prompt and seeds hand-written recipes. Synced via an optional `SyncRecipeDto.language`, with `dto ?: existing` on pull so an older backend can't wipe it. Room v10→v11. **Amended:** pre-existing recipes were backfilled to `en` server-side (backend `fix_recipe_language_backfill_en.sql`, bumping `server_updated_at`); devices pick it up through sync, and recipes the server never sees (anonymous sessions, never-pushed) stay `null` — no Room migration. |
| 017 | [Cook History Sync](../adrs/adr-017-cook-history-sync.md) | Oct 2026 | `recipe_cook_events` (#273/#294) now syncs as an **event log piggybacked on push/pull** (`cookEvents`, backend Chef.ai_Backend#107), not LWW documents: the client-generated event id is the idempotency key, un-marking pushes the same id with `deletedAt` and **a tombstone is final**, re-marking mints a new id — so no resurrection and no conflicts list. The entity becomes `SyncableEntity` (Room v14→v15; existing rows backfill `PENDING` so they upload); un-mark tombstones instead of deleting and `observeCookedRecipeIds` excludes tombstones. Push guards `SYNCED` with `expectedUpdatedAt`; `EVENT_ID_TAKEN` re-keys a live event (drops a tombstone), validation errors park the row `CANCELLED`. Pull applies idempotently, is unpaginated and does not move the cursor. Per-user, never household-shared. |
| 018 | [Saved Meal Plans](../adrs/adr-018-saved-meal-plans.md) | Nov 2026 | A saved plan is a **template snapshot** in its own `saved_meal_plans` row (Room v15→v16), not a flag on `meal_plans`: title (≤ 60), preferences and the generated lineup minus cooked marks, copied once from the wizard's freshly generated plan, so later edits to that plan, deleting it, or a regeneration never touch it. Lineup is a `daysJson` column with **no FKs** (as ADR-017); Repeat drops locally soft-deleted recipes but keeps unknown ids, and copies the days into a new dated plan without calling the generator. The hero photo is **device-local** (`saved_plan_images/`, never synced, falls back to a recipe image); upload via ADR-012 is deferred. Syncs as LWW documents on push/pull (`savedMealPlans`, backend Chef.ai_Backend#118, server filters on `server_updated_at`); `SAVED_PLAN_ID_TAKEN` re-keys, other errors park `CANCELLED`; pull unpaginated, skipped without an authenticated user; per-user, never household-shared. |
